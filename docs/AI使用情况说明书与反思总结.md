## 二、关键 AI 使用案例

### 案例 1：Anthropic 模型适配器 -- 架构设计

#### 1. 任务目标

用户通过 micuapi.ai 中转站访问 Anthropic Claude 模型（`claude-sonnet-4-6`），但中转站对 `claude-` 前缀的模型名称强制使用 Anthropic 原生 Messages API 协议，而非 OpenAI 标准的 Chat Completions 协议。直接使用 OpenAI SDK 请求会返回 HTTP 400 错误。需要在**不修改路由层和应用层代码**的前提下，使系统透明地支持 Claude 模型。

#### 2. 使用的 Prompt 策略

采用**分阶段引导**策略：

- **第一阶段（问题诊断）**：向 Claude Code 描述具体错误现象（"配置 claude-sonnet-4-6 后调用 API 返回 400"），要求 AI 分析可能的原因并给出排查路径。
- **第二阶段（方案设计）**：明确约束条件（"路由层已经为 OpenAI 接口编写，不能改动"），要求 AI 提出解耦方案。
- **第三阶段（实现细化）**：要求 AI 生成符合 OpenAI `chat.completions.create()` 接口签名的包装器代码，同时处理流式和非流式两种模式。

#### 3. AI 响应摘要

Claude Code 提出了 **Adapter 模式**的设计方案：

- 创建 `AnthropicAdapter` 类，对外暴露 `client.chat.completions.create()` 接口（与 OpenAI SDK 一致）
- 内部将 OpenAI 格式的 `messages` 列表拆分为 Anthropic 需要的 `system`（独立参数）+ `messages`（仅 user/assistant）
- 通过 `_Response`、`_StreamChunk`、`_Delta`、`_Choice` 等轻量包装类模拟 OpenAI 响应结构
- `_StreamWrapper` 懒迭代 Anthropic stream，对调用方透明

#### 4. 人工修改与验证

学生对 AI 方案做了以下关键修改：

1. **架构决策（学生独立）**：选择 Adapter 模式而非修改 `routes/api.py` 的路由逻辑。理由：`_init_ai_client()` 在 `app.py` 中通过检测模型名前缀（`claude-`）自动选择 OpenAI SDK 或 AnthropicAdapter，路由层完全无感知。这符合开闭原则（OCP）-- 扩展新模型支持时无需修改现有路由代码。

2. **Temperature clamp**：Anthropic API 的 temperature 范围是 `[0, 1]`，而 OpenAI 是 `[0, 2]`。学生在 `_Completions.create()` 中添加了 `max(0.0, min(float(temperature), 1.0))` 的 clamp 逻辑，防止传入 1.5 等值导致 400 错误。

3. **流式模式验证**：学生手动测试了流式 SSE 推送（通过前端聊天界面逐步输出答案），确认 `_StreamWrapper` 的 `yield _StreamChunk(text)` 逻辑与 SSE 事件循环兼容。

4. **非流式模式验证**：通过 API 调用测试确认 `_Response` 包装类的 `resp.choices[0].message.content` 访问路径与 OpenAI 响应对象一致。

5. **懒导入优化**：`import anthropic` 放在 `AnthropicAdapter.__init__()` 内部，确保不使用 Claude 时不会触发缺失依赖报错。

#### 5. 最终结果

- `ai/anthropic_adapter.py`（163 行）实现了一个完整的协议适配器
- 所有 276 个测试用例通过，路由层和 AI 模块无需任何修改
- 用户在前端配置界面输入 `claude-sonnet-4-6` 模型名后，系统自动切换到 Anthropic 协议
- 此设计具备良好的扩展性：未来支持 Google Gemini、Cohere 等其他协议时，只需新增 Adapter 类

### 案例 2：Plotly 5.x 二进制编码问题 -- 深度 Debug

#### 1. 任务目标

用户在 Amazon BestSelling Books 数据集上提问"画 Rank 和 Price 的散点图"后，图表只显示坐标轴和背景，没有任何数据点。同时控制台报错 `Object of type ndarray is not JSON serializable`。

#### 2. 使用的 Prompt 策略

- **初始尝试**：直接向 AI 描述现象，要求修复散点图空白问题。AI 建议用 `fig.to_json()` + `json.loads()` 替代 `fig.to_plotly_json()`。
- **失败后重新引导**：AI 的初步修复未能解决空白问题，学生决定采用**系统性排查**策略 -- 在服务端添加诊断代码（`print(type(x_data), x_data[:5] if hasattr(x_data, '__getitem__') else x_data)`），捕获实际返回的数据结构。

#### 3. AI 响应摘要

在学生的指导下，AI 分析诊断输出后发现关键问题：

服务端返回的 `x` 数据格式是：
```json
{"dtype": "f8", "bdata": "AAAAAACAv0A..."}
```

而非预期的：
```json
[1.0, 2.0, 3.0, ...]
```

AI 解释这是 **Plotly 5.x 的新特性**：`to_dict()` 和 `to_json()` 将 numpy 数组序列化为 Base64 编码的二进制格式以减少体积。但浏览器端的 Plotly.js 版本不支持解码此格式，导致 `x`/`y` 被当作空对象处理，图表渲染为空坐标轴。

#### 4. 人工修改与验证

学生的深度参与在此案例中尤为关键：

1. **根因定位（学生主导）**：AI 最初建议的 `to_json()` 方案未能解决问题。学生通过阅读 Plotly 5.x 的变更日志和源码，确认了二进制编码机制是 Plotly 5.0 引入的特性。服务端 Plotly 是 5.x 版本，而前端 CDN 加载的 Plotly.js 是较旧版本，版本不匹配导致解码失败。

2. **`_decode_plotly_bdata()` 递归解码器（学生设计）**：向 AI 描述了需要递归遍历整个 Figure dict、检测 `{dtype, bdata}` 模式并用 `base64.b64decode` + `numpy.frombuffer` 解码的完整方案。AI 据此生成了递归函数代码。

3. **`_plotly_fig_to_dict()` 统一入口**：学生设计了从 `fig.to_dict()` -> `_decode_plotly_bdata()` 的完整序列化链路，替代了原来碎片化的 `to_json()`/`to_plotly_json()` 路径。

4. **多重修复验证**：
   - 用 `Amazon_BestSelling_Books_500.csv` 测试 Rank vs Price 散点图，确认数据点正确显示
   - 发现并修复了 `_ensureMarkerVisibility()` 中 `Object.assign` 参数顺序错误（`Object.assign({}, defaultMarker, trace.marker)` 应为 `Object.assign(defaultMarker, trace.marker || {}, ...)`）
   - 同时处理了 `ndarray` 序列化问题（`_json_serial` 回调函数）

#### 5. 最终结果

- 散点图在所有测试数据集上正确显示数据点
- `_decode_plotly_bdata()` 实现了递归解码，理论上兼容所有 Plotly 图表类型的二进制编码
- 此修复为后续的通用数据集支持改造铺平了道路

### 案例 3：数据预处理可视化 -- 全链路改造

#### 1. 任务目标

数据概览页面的"清洗前后数据量对比图"显示范围为 -1 到 1，所有数据点为 0，视觉上完全空白。需要修复并改进为有意义的预处理流水线可视化。

#### 2. 使用的 Prompt 策略

- 首先描述问题现象，要求 AI 检查 `preprocess_visual` 方法的数据读取逻辑
- 确认根因后，要求 AI 设计更有信息量的可视化方案
- 分步指导：先修键名，再优化图表布局

#### 3. AI 响应摘要

AI 最初的分析认为 `preprocess_visual` 方法读取了错误的 `pp_report` 键名。深入排查后发现：

- 代码中使用 `pp_report.get("duplicates_removed")` 读取去重数据
- 实际返回结构中，该数据嵌套在 `pp_report["remove_duplicates"]["removed"]` 路径下
- 由于键名匹配失败，所有计数器默认为 0，导致流水线各阶段的值全为 0

AI 提出了重写方案：将朴素的"清洗前后对比"改为 **三阶段流水线柱状图**（原始数据 -> 去重后 -> 无效过滤后），每个阶段显示行数变化和差异标签。

#### 4. 人工修改与验证

学生的关键贡献：

1. **根因分析（学生主导）**：通过阅读 `data/preprocessor.py` 的 `run_all()` 方法源码，定位到 `pp_report` 的实际嵌套结构（`remove_duplicates.removed`、`filter_invalid_records.removed`、`handle_missing`）。AI 最初建议的键名列表不完整，学生补充了所有三个键的完整路径。

2. **缺失率热力图溢出修复**：发现缺失率柱状图在仪表盘卡片中溢出容器。学生分析了 CSS 布局问题后，指导 AI 在图表配置中添加动态高度计算和 `overflow:hidden` 样式。

3. **Pipeline 数据重构算法**：学生设计了从 `rows_final` 反推 `rows_after_inv` 和 `rows_orig` 的计算逻辑（`rows_final + inv_removed = rows_after_inv`，`rows_after_inv + dup_removed = rows_orig`），确保流水线可视化反映真实的数据变化量。

4. **涉及文件协调**：修改了 `data/analyzer.py`（后端数据生成）、`routes/api.py`（API 端点）、`templates/index.html`（图表容器）、测试文件（4 个文件同步修改）。

#### 5. 最终结果

- 预处理流水线可视化正确显示三阶段行数变化
- 缺失率热力图不再溢出容器
- Chart.js 替换为 ApexCharts，实现了更好的响应式兼容

### 案例 4：通用数据集支持改造 -- 系统架构升级

#### 1. 任务目标

系统最初的设计围绕零售交易数据集（Online Retail 数据集）展开。切换其他类型数据集（如书籍评分数据、纯分类调查数据、时间序列数据）时，出现图表空白、分析错误、建议问题不适用等问题。需要实现**全数据集通用化**。

#### 2. 使用的 Prompt 策略

- 先要求 AI 分析当前系统中硬编码的零售业务逻辑（列名关键词、分析假设）
- 然后要求 AI 设计一个数据集画像系统，自动识别数据类型并提供差异化分析
- 分 11 个子任务逐步实现（每步提交并验证）

#### 3. AI 响应摘要

Claude Code 提供了以下方案：

- 创建 `DataProfiler` 类，通过列名关键词匹配 + 数据特征检测自动识别 6 种数据画像：零售交易型、时间序列型、科学数值型、分类调查型、地理分布型、混合型
- 根据画像类型生成自适应图表配置和差异化建议问题
- 为宽数据集（大于 25 列）添加截断逻辑，防止 AI 提示词过长

#### 4. 人工修改与验证

学生的关键架构决策：

1. **6 种画像分类体系（学生设计）**：AI 最初提议 4 种画像。学生分析常见数据科学场景后，将分类扩展为 6 种，并设计了关键词库（正则模式匹配列名中的 date/customer/product/amount/geo 语义）。

2. **纯分类数据降级策略（学生设计）**：AI 的方案中，纯分类数据集（如调查问卷数据）会因为没有数值列而生成空白图表。学生设计了降级策略：当检测到分类型画像且无数值列时，自动将散点图和分布图替换为频次柱状图。

3. **建议问题生成算法的调优**：AI 生成的建议问题偏向通用模板。学生为每种画像类型定制了问题生成逻辑，确保建议问题与数据集的实际列名挂钩（如 `"按 {date_col} 展示数值趋势折线图"`）。

4. **11 个子任务的流程管理**：学生设计了从画像检测 -> 列信息注入 -> 自适应图表 -> API 端点 -> 前端适配的完整实现顺序，使用 git 逐任务提交（最终 12 个 commits）。

5. **276 测试回归验证**：每完成一个子任务都运行全量测试，确保不引入回归。

#### 5. 最终结果

- `data/profiler.py`（230 行）实现 6 种数据画像自动检测
- 新增 5 个通用化 API 端点（data_profile、adaptive_charts、suggested_questions、download_clean、preprocess_visual）
- Analyzer 新增 5 个通用分析方法（distributions、scatter、box、preprocess_visual、category_distributions）

### 案例 5：代码安全沙箱 -- 多层防护体系

#### 1. 任务目标

系统核心功能之一是让 AI 生成 Python 代码并在服务端执行（`exec()`）。必须在不影响正常数据分析功能的前提下，建立可靠的安全防护机制，防止恶意代码执行或意外系统访问。

#### 2. 使用的 Prompt 策略

- 要求 AI 枚举 `exec()` 执行用户生成代码的所有安全风险点
- 要求 AI 生成安全校验代码（危险函数黑名单、受限内置函数）
- 逐步完善：先基础防护，再补充边界情况

#### 3. AI 响应摘要

Claude Code 提出了一个多层防护方案：

- 危险关键词黑名单（`_FORBIDDEN`）：`import os`、`import sys`、`subprocess`、`open(`、`__import__`、`eval(` 等
- 受限内置函数白名单（`_SAFE_BUILTINS`）：仅保留 `len`、`range`、`sorted`、`sum` 等安全函数
- 代码净化（`_sanitize_code`）：移除所有 import 语句
- 受限命名空间注入：仅提供 `pd`、`np`、`json` 和安全的 `__builtins__`
- 线程超时机制：`threading.Thread` + `done_event.wait(timeout=30)`

#### 4. 人工修改与验证

学生的关键安全决策：

1. **防护顺序调整（学生独立发现并修复）**：AI 最初将 `_sanitize_code()` 放在 `validate_code()` 之前执行。学生发现这是一个严重的安全漏洞 -- 如果攻击者的代码中包含 `import os`，净化后会变成空行，但其他危险关键词（如 `subprocess` 不在 import 行中）仍会通过。**正确的顺序必须是先 validate 后 sanitize** -- 先检测原始代码中的危险关键词，再移除无危险的 import 语句。

2. **`ndarray` 序列化问题**：AI 生成的沙箱代码返回 numpy ndarray 时，Flask 的 `jsonify()` 会抛出 `Object of type ndarray is not JSON serializable` 异常。学生指导 AI 添加了 `_serialize()` 和 `_json_serial()` 递归序列化函数，将 numpy 类型转为 Python 原生类型。

3. **`go.Figure` 自动检测与转换**：当 AI 生成的代码创建 `go.Figure` 对象并赋值给 `chart` 时，需要自动调用 `.to_dict()` 序列化。学生添加了 `_plotly_fig_to_dict()` 检测逻辑。

4. **`_FORBIDDEN` 列表的审计**：学生逐项审查了黑名单关键词，补充了 `shutil`、`pathlib`、`socket`、`globals(`、`locals(`、`compile(`、`breakpoint(` 等遗漏的高危条目。

5. **超时后线程处理**：Python 的 `threading.Thread` 无法被强制杀死。学生设计了 daemon 线程 + `done_event` 的方案，超时后返回错误信息但不阻塞主进程。

#### 5. 最终结果

- 沙箱防护包含 6 层安全机制（黑名单过滤 -> 白名单限制 -> 代码净化 -> 受限命名空间 -> 线程超时 -> 结果安全序列化）
- 所有危险操作（文件读写、系统调用、动态导入）均被拦截
- 276 个测试中包含了安全沙箱的边界测试
- 防护顺序 Bug 在代码审查中发现并修复，未进入生产环境

## 三、AI 能力边界总结

### 3.1 AI 擅长的领域

| 领域 | 具体表现 | 典型案例 |
|------|----------|----------|
| **代码骨架生成** | 给定清晰的设计规范，AI 能快速生成结构完整的类和方法框架 | DataProfiler 的 6 个检测方法骨架 |
| **模式识别与迁移** | AI 能快速识别现有代码的模式，并应用于新场景 | Adapter 模式从概念到代码的转换 |
| **文档查询与整合** | 通过 Context7 MCP，AI 能准确查询 pandas/plotly API 用法 | 各类 API 调用的参数验证 |
| **重复性工作** | 测试用例生成、错误处理模板、序列化/反序列化代码 | 20 个测试文件的初始版本 |
| **代码解释与教学** | 当学生对某段代码有疑问时，AI 能给出清晰的解释 | Plotly 二进制编码机制的讲解 |

### 3.2 AI 的局限性

| 局限性 | 具体表现 | 实际遇到的案例 |
|--------|----------|---------------|
| **缺乏项目全局上下文** | AI 不了解项目的完整架构和所有约束条件 | 建议在路由层直接调用 Anthropic SDK 而非 Adapter 模式 |
| **版本兼容性盲区** | AI 的训练数据覆盖多个版本，但不能精确感知当前环境的具体版本差异 | Plotly 5.x 的二进制编码与旧版 Plotly.js 的兼容性问题 |
| **幻觉 (Hallucination)** | AI 会"猜测"不存在的 API 或 JSON 键名 | `pp_report.get("duplicates_removed")` -- 实际键名是 `remove_duplicates.removed` |
| **被动响应** | AI 不会主动发现运行时 Bug，必须由人类提供具体错误信息 | 所有 Bug 都是学生在测试中发现后报告给 AI 的 |
| **安全盲点** | AI 能生成安全代码，但不能保证生成的代码天然安全 | `_sanitize_code` 与 `validate_code` 的顺序问题 |

### 3.3 关键发现

**"已知模式" vs "未知边界"**：

AI 在"已知模式"内表现优秀 -- 当问题可以归纳为"生成一个 X 模式的数据处理管道"或"为 Y 类添加单元测试"时，AI 的输出质量很高。但当问题落在"未知边界"上 -- 如特定版本的兼容性 Bug（Plotly 5.x）、运行时错误的具体根因（JSON 键名不匹配） -- AI 表现出显著的局限性，必须由人类提供诊断信息和引导方向。

**结论**：在本项目中，AI 的角色更接近于一个能力极强的"高级工程师"，而非"架构师"或"QA"。它擅长在明确的设计规范下高效编码，但战略性的架构决策、系统性的 Debug 思路、以及对安全/质量的终极把关，始终需要人类开发者来主导。

## 四、学生关键决策与贡献

以下列出在本项目中由学生独立做出的 10 项关键决策，这些决策塑造了项目的架构、质量和成功率。

### 1. Adapter 模式解耦模型接入（架构设计层面）

当面对 Anthropic API 协议差异时，AI 最初建议在 `routes/api.py` 中增加条件分支检测模型名。学生拒绝了该方案，选择创建独立的 `AnthropicAdapter` 类，通过 `_init_ai_client()` 的模型名检测实现自动路由。这符合 SOLID 原则中的开闭原则（OCP）和单一职责原则（SRP）。

### 2. Plotly 二进制编码的深度排查思路（Debug 能力）

当 AI 的初步修复（`to_json()` 方案）未能解决问题时，学生设计了系统性的诊断流程：添加服务端诊断日志 -> 分析输出格式 -> 查阅 Plotly 5.x 变更文档 -> 定位版本不兼容根因 -> 设计递归解码器。这一过程中每一步都需要人类的数据直觉和系统思维。

### 3. 安全防护的防护顺序设计（安全设计）

学生审查代码时发现 `validate_code()` 必须在 `_sanitize_code()` 之前执行，否则攻击者可以利用净化步骤绕过黑名单检测。这是一个需要理解代码执行流程和攻击向量才能发现的逻辑漏洞。

### 4. 通用数据画像的分类体系设计（领域建模）

AI 最初建议 4 种数据画像类型。学生基于数据科学中的常见场景，将分类扩展为 6 种（retail/temporal/numeric/categorical/geographic/mixed），并设计了关键词检测规则和优先级分类算法。

### 5. 全链路数据追踪的流水线可视化设计

将原本简单的"清洗前后对比"图表升级为三阶段流水线可视化，展示数据从原始 -> 去重 -> 无效过滤的完整行数变化轨迹。这一设计体现了数据工程中的 Pipeline 思维。

### 6. 项目三层分离的模块化架构

`ai/`（AI 交互层）、`data/`（数据处理层）、`routes/`（API 路由层）的三层分离由学生独立设计。AI 在每层内部提供了实现帮助，但层与层之间的职责边界和数据流向由学生定义。

### 7. SSE 流式连接的统一抽象

Flask 的 SSE（Server-Sent Events）流式推送需要处理多种数据格式（文本 token、图表数据、状态更新）。学生设计了统一的事件格式（`{event: "text"|"chart"|"status", data: ...}`），前端通过 `EventSource` 统一接收和路由。

### 8. 前端图表工作台的双向同步机制

在分析结果展示区域和图表编辑工作台之间实现了双向实时同步：用户在任一位置修改图表配置，另一位置自动更新。这涉及全局状态管理（`window._currentChartData`）、事件监听、以及 Plotly 实例的跨容器重新渲染。

### 9. 纯分类数据的自适应降级策略

检测到纯分类数据集（无数值列）时，系统自动将数值分析类图表降级为频次柱状图和饼图。这一决策由学生在测试 Books 数据集时发现问题后独立提出并实现。

### 10. CSV 分隔符自动嗅探

原始的数据加载仅支持逗号分隔的 CSV。学生在测试多个公开数据集后发现某些数据集使用分号、制表符、管道符分隔。设计了基于 `csv.Sniffer` 的自动检测逻辑，兼容 4 种常见分隔符。

## 五、AI 生成内容中被拒绝或重写的部分

### 5.1 被拒绝的初步方案：路由层硬编码协议分支

**AI 建议**：在 `routes/api.py` 的 `_init_ai_client()` 中添加 `if "claude" in model: use anthropic SDK; else: use openai SDK`。

**拒绝原因**：这违反了开闭原则。每次新增模型协议都需要修改路由层代码。学生选择了 Adapter 模式，使路由层对协议差异完全无感知。

### 5.2 被重写的错误键名假设

**AI 生成**：`data/analyzer.py` 中 `preprocess_visual` 方法直接使用了 `pp_report.get("duplicates_removed")`。

**问题**：AI 没有查看 `preprocessor.py` 的实际返回结构就假设了键名。实际返回结构是嵌套的 `{"remove_duplicates": {"removed": N}, ...}`。

**修复**：学生阅读了完整的 `run_all()` 方法源码，定位到正确的键路径，重写了整个数据提取逻辑。

### 5.3 被修正的安全防护顺序

**AI 生成**（原始代码）：
```python
code = _sanitize_code(code)     # 先净化
if not self.validate_code(code): # 再校验
    return error
```

**问题**：净化会移除 import 语句，但不会移除 `subprocess.call(...)`、`open("/etc/passwd")` 等非 import 的危险操作。如果攻击者将这些危险代码放在 import 行之外，净化后它们仍然存在。

**修复**：学生将顺序反转为先 `validate_code(原始code)` 后 `_sanitize_code(code)`。

### 5.4 被改进的弱安全黑名单

**AI 生成**：最初的 `_FORBIDDEN` 列表仅包含 `import os`、`import sys`、`subprocess`、`__import__`、`eval(`、`exec(`、`open(`。

**问题**：遗漏了 `shutil`（文件操作）、`pathlib`（路径遍历）、`socket`（网络连接）、`globals(`（命名空间逃逸）、`locals(`、`compile(`、`breakpoint(`。

**修复**：学生逐项审计后补充了 6 个遗漏的高危关键词，使黑名单覆盖更全面。

### 5.5 被优化的过度截断策略

**AI 建议**：对宽数据集（大于 25 列），AI 提示词中只列出列名，不包含数据类型和样本值。

**学生决定**：保留数据类型和样本值（前 3 个），仅截断列数。理由：样本值对 AI 理解列语义至关重要（如 `CitricAcid` 列的样本值 `[0.49, 0.0, 0.32]` 远比列名本身更能帮助 AI 判断这是一个数值特征）。

### 5.6 被简化的过度设计的图表配置

**AI 生成**：`_ensureMarkerVisibility()` 函数试图通过复杂的深拷贝策略覆盖 Plotly trace 的所有 marker 属性。

**问题**：`Object.assign` 参数顺序错误（空对象在前，覆盖了原有配置），加上过度设计导致难以调试。

**修复**：学生简化为分层合并策略 -- 先保留 trace 原始 marker，再增量覆盖缺失属性。

## 六、AI 辅助编程的价值与局限性反思

### 6.1 效率提升量化

| 开发活动 | 传统方式估计 | AI 辅助实际 | 效率提升 |
|----------|-------------|------------|----------|
| 代码骨架生成（DataProfiler） | 3-4 小时 | 30 分钟（AI 生成）+ 1 小时（学生审查调整） | 70% |
| 单元测试编写（20 个测试文件） | 8-10 小时 | 3 小时（AI 生成）+ 2 小时（学生审查补齐） | 50% |
| Bug 修复（Plotly 二进制编码） | 4-6 小时 | 2 小时（学生诊断）+ 1 小时（AI 辅助修复） | 50% |
| Adapter 模式实现 | 3-4 小时 | 45 分钟（AI 生成）+ 30 分钟（学生调整） | 70% |
| API 端点新增（5 个端点） | 6-8 小时 | 2 小时（AI 生成）+ 2 小时（学生调优） | 50% |

**总体估算**：AI 辅助编程使本项目开发效率提升约 **50-70%**，主要体现在减少重复性编码（测试、序列化、错误处理）和加速代码骨架搭建上。

### 6.2 质量保障

**测试覆盖率**：AI 生成了约 70% 的测试代码，但学生审查了每一个测试用例的断言逻辑，并补齐了边界条件测试（如空数据集、极端值、类型错误场景）。最终 276 个测试全部通过。

**代码审查必要性**：AI 生成的代码必须经过人工审查。本项目中发现的多处关键 Bug（安全防护顺序、键名错误、Object.assign 参数顺序）都是学生审查时发现的，而非 AI 自动检测到的。

**安全审查的不可替代性**：AI 能生成安全代码，但不能保证代码安全。沙箱防护的审计、黑名单的补充、防护顺序的校正，都需要开发者具备安全领域的专业知识。

### 6.3 学习价值

**通过 AI 解释加深理解**：当遇到 Plotly 5.x 的二进制编码问题时，AI 提供了编码机制的详细解释，帮助学生快速理解了底层原理。这种"即时专家辅导"是 AI 辅助编程的重要学习价值。

**通过讨论锻炼架构思维**：在与 AI 讨论 Adapter 模式 vs 直接修改路由层的方案时，学生需要清晰地表达架构取舍的理由，这一过程锻炼了架构设计的表达和决策能力。

**通过审查提升代码品味**：持续审查 AI 生成的代码让学生养成了批判性阅读代码的习惯，学会识别"能工作但不优雅"的代码。

### 6.4 风险意识

**过度依赖的风险**：如果开发者不审查 AI 生成的代码就直接使用，本项目至少会有 4 处已发现的关键 Bug 进入代码库（安全漏洞、键名错误、渲染 Bug、同步失效）。AI 辅助编程的前提是开发者具备独立判断能力。

**"AI 能写一切"的错觉**：AI 在已知模式内表现优秀，但在面对版本兼容性、特定业务逻辑、安全性边界等问题时可能产生错误输出。本项目中 Plotly 5.x 问题的排查过程充分说明了：**真正困难的不是写代码，而是知道需要写什么代码**。

**上下文窗口限制**：Claude Code 每次对话有上下文窗口限制（200K tokens），对于大型代码库，AI 可能无法一次加载所有相关文件。本项目通过分模块、分子任务的方式规避了这一限制 -- 每次对话聚焦单一模块，避免跨模块的上下文污染。

**最终认识**：AI 辅助编程的最大价值在于将开发者从重复性编码中解放出来，使其能专注于更高层次的思考 -- 架构设计、安全审查、用户体验、系统集成。但最具创造性和最具风险的部分（设计决策、安全把关、质量验证）始终需要人类来完成。AI 是强大工具，但不是替代品。
